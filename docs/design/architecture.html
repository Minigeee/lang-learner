Architecture

A C4 walk through the language-learning app, from its place in the world down to the contracts that keep it extensible. Adding a unit is a content change only. Adding a language is a language pack, content and one registration line, with no change to the core.

Proposal, revision 4.02026-11-13 Revision 4.0 applies the owner's stack decision of 2026-11-13 (README Stack row). The only runtime third parties are Tailscale and one VPS provider. One small Node server of our own (apps/server) on a rented VPS serves the Vue web app, its content and audio, and two sync endpoints over a SQLite file. It listens only on localhost, and tailscale serve exposes it over HTTPS to the tailnet alone, so being on the tailnet is the sign-in. The app runs in a browser on the laptop and phone, installs as a PWA, and works offline after its first load. The event log and the Remote port are unchanged; only the adapter changes. Supabase, the sync key, Tauri and the bundled-app builds are gone, and decisions 12–14 are superseded (§13). Revision 3.0 (2026-11-08) made the app a Tauri v2 app with its content bundled in, and Supabase Free an events-only database behind a sync key; it superseded decisions 1, 2 and 5. Revision 2 applies the adversarial review (dispositions at its end) and the owner's answers: a private repo, a phone and a laptop used daily, simplified Mandarin only, no second language soon, at most about $10 a month, as few services as possible, and content pipelines run on the owner's laptop (RTX 2070). Revision 2.1 keeps the content bundle private in Supabase Storage. Revision 2.2 applies the sync-replay and authoring-format spikes and the Phase 0 plan: clients write only through a serialized push_events function, sync moves into core behind ports, days close by the settled rule, and the widget and language pack contracts state more of what they promise. Revision 2.3 applies the Phase 1 plan: the compiled lesson shape moves to packages/core/content.ts, the curriculum is plain data, Node does every upload, the dependency check uses the unit closure, and lesson slots are the decided arc. It builds on the research synthesis, the UI flow and the unreviewed data-model TDD, which this doc overrides where they differ (§13).

4. Level 3: Components

App

Four layers with downward-only dependencies, plus the language pack on the side. The pack has two halves: logic, which is plain TypeScript implementing core interfaces, and views, which are Vue components for the pack's own item kinds and widgets. The app wires both in through one registration file. Core code calls the pack only through the interface, and never imports it.

Vue (apps/web)No Vue (packages/core, app adapters)Language pack

The rules are enforced by package dependencies plus one dependency-cruiser config:

  • packages/core imports nothing from the app or the languages, and never Vue.
  • languages/*/logic imports only packages/core.
  • languages/*/views may import Vue and packages/core.
  • Only apps/web/src/languages.ts imports packs.
  • apps/server imports only packages/core, and never Vue or a pack.

5. Event log and sync

The whole user state is one append-only table: in one SQLite file on the server, with a full copy on every device. Everything else, including card schedules, is folded from it on the device. This replaces the earlier mix of facts plus mutable card rows, which two devices could corrupt (review B2).

-- apps/server/schema.sql. No user_id: one owner on one tailnet, so every row is the owner's.
-- A second user would need real accounts and a column, which is a new migration; none is planned.
create table events (
  seq         integer primary key autoincrement,   -- commit order, because pushes are serialized; the pull cursor. Never reused
  id          text not null unique,                -- client-generated uuid v7 (or deterministic, see below)
  kind        text not null,                       -- see the Event union in §6
  v           integer not null,                    -- payload schema version for this kind
  lang        text,                                -- language of the item involved; null for global events
  occurred_at integer not null,                    -- device stamp in integer ms (§6); ordering for derive
  device_id   text not null,
  device_seq  integer not null,                    -- per-device counter, so a gap is detectable
  build       text not null,                       -- app+content build id that wrote it
  payload     text not null check (json_valid(payload))
) strict;                                          -- the file runs in WAL mode, and apps/server is its only writer
-- apps/server: the only routes that touch events. They take no key: reaching the server at all
-- means being on the tailnet. Bodies are JSON in the camelCase envelope of §6.

-- Validates every event's envelope, and the payload of every kind and v the server knows (a device
-- can't run a newer build than the server, since both ship in one deploy). A malformed event comes back
-- with its error and doesn't abort the batch. The valid ones are inserted in one immediate transaction,
-- so pushes are serialized and seq order equals commit order. Idempotent: a known id is skipped.
POST /sync/push   { events: EventEnvelope[] }  ->  { rejected: { id, error }[] }

-- Up to limit events with seq > after, in seq order. The server may return fewer than limit;
-- only an empty page means the caller has caught up.
GET  /sync/pull?after=<seq>&limit=<n>       ->  { events: EventEnvelope[] }

Write and push

  • An event and its outbox entry are written locally in one atomic step, and the outbox drains first in, first out.
  • Push calls POST /sync/push, the only client write path. The server runs insert … on conflict (id) do nothing in one immediate SQLite transaction, so pushes are serialized and retries are harmless.
  • The outbox flushes on launch, on visibilitychange, on online, and on Sync now in Settings. Nothing syncs while the app is closed.
  • An unreachable server (offline, off the tailnet, or down) leaves the outbox as it is and shows in Settings; the app keeps working from its local log.
  • A permanently rejected event (a schema error) is moved to a dead-letter list shown in Settings, so it can never wedge the queue.

Pull

  • GET /sync/pull?after=<cursor>&limit=<n>, paged until a page comes back empty. seq is assigned on arrival, so events that sync late from an offline device are still pulled. Serialized pushes keep seq order equal to commit order, so a row can't commit behind the cursor and be skipped.
  • A pull overwrites the local copy by id: the server row is authoritative for an id. Deterministic-id events depend on this, because two devices can write different payloads under one id.
  • Derive orders by occurredAt (tie-break by id), never by seq.

Cards

  • A card's id is deterministic: hash(itemId, cardTemplate), so two devices adding the same card produce one card.
  • Its schedule is rebuilt by replaying its review events in time order through FSRS. ts-fsrs seeds its fuzz from cardId + reps, which needs fuzz turned on and a cardId passed to newCard() every time.
  • The load balancer reads the device's current due counts, so it can't be replayed. Each review records the chosen date as review.dueAt, guarded by prevReviewId: replay uses dueAt only if prevReviewId matches the replayed previous review, and otherwise falls back to seeded fuzz. Both branches are deterministic.
  • Concurrent offline reviews on two devices both count, in time order. Nothing is overwritten.

Frozen history

  • A study day runs in the synced studyTz from dayStartHour; derive never reads the device's time zone. The day stays open, with provisional XP and credit, until it settles.
  • Each device records a device hello on first launch, before any study, and pushes it on its first successful flush, so the others know it exists.
  • Right after a successful pull, never offline, any device may append day_closed with that day's XP, consistency credit and rule versions. It may do so once either of these holds:
    • every other device that recorded anything in the 14 days before the day's end has an event stamped at or after that end (basis settled);
    • 72 hours have passed since the day's end (basis grace).
    Both windows are owner-tunable.
  • The id is hash(date) (one owner, so the date alone names the day), so two closes share one id. The server keeps the first, and the other device converges on pull.
  • Events that arrive after a close still count for cards, mastery and input hours, but never change that day's XP or credit. No note is shown.
  • XP and study days for closed days are read from these events, never recomputed. Rule or content changes apply from today on.
  • Mistakes are corrected with void events, never by deletion. A void can't target a day_closed; a correction there is a later rule version.

A full recompute over a year of events (roughly 150k) takes about 5 s on a mid-range phone, a figure scaled from a laptop measurement by an assumed 4×. That's too slow to run on every log change, so a per-card cache is needed. Each card's derived state is stored with its rules and FSRS versions and its last applied review: a later review applies directly, and an older event replays just that card. Mastery uses a similar per-item fold, and XP only needs the open days. A full recompute runs only when the rules or the FSRS version change, in a Web Worker. There's no server-side fallback until a measurement says otherwise (review m1).

6. Level 4: Key contracts

Ids

// packages/core/ids.ts: one grammar, enforced at every boundary. A non-NFC id is rejected there, never normalized.
type Lang = string                               // a language, not a script: 'zh'. Script and region are display settings of a pack
type ItemId   = `${Lang}:${string}:${string}`    // lang : kind : key. zh:w:行:hang2 · zh:g:le-completion · zh:c:好
type LessonId = `${Lang}:les:${string}`          // also unit and stage
type CardId   = `card:${string}`                 // hash(itemId, template): deterministic across devices
type MediaId  = `media:${string}`                // media, clips, speakers, licenses are global and tagged with a language
// Core kinds: 'w' lexical item, 'g' grammar point, 'sc' sound contrast, 'sr' sound rule.
// A pack registers more: zh adds 'c' character and 'cmp' component.

The language pack

// packages/core/language.ts
interface LanguagePack {                          // languages/<lang>/logic: no Vue, shipped in the app, lazy-loaded
  code: Lang; name: string
  normalize(s: string): string                    // after NFC: zh none; ja width folding; es none
  analyze(sentence: string, lex: Lexicon): Analysis   // tokens with surface, lemma, the reading chosen in context, ruby segments, features
  itemKey(entry: LexEntry): string                // a stable natural key, many-to-one over dictionary entries: zh 行:hang2, ja 食べる:たべる, es comer:v
  itemKinds: ItemKindDef[]                        // extra kinds, with zod schemas used at build time only
  soundAxes: string[]                             // zh ['tone','initial','final']; es ['vowel','r-rr']; ja ['mora','pitch']
  cardTemplates: CardTemplate[]                   // which card faces each kind gets (zh: hanzi→meaning, audio→meaning)
}
interface LanguagePackBuild extends LanguagePack { // languages/<lang>/build: Node only
  lexicon: LexiconBuild                           // imports dictionary datasets into sharded, license-tagged files
  syllabi: SyllabusDef[]                          // hsk2025 levels: tags, never structure
  seedEdges?(items: KnowledgeItem[]): Edge[]
  checkRules?: CheckRule[]                        // optional extra lint
  mediaSources: MediaSourceAdapter[]              // used by the ingester
}
interface LanguagePackViews {                     // languages/<lang>/views: Vue
  itemDetail: Record<string, Component>           // per pack-specific kind
  widgets?: Record<string, Component>
  Ruby: Component                                 // renders an analyzed sentence with readings
}

Target-language text is never detected by heuristics. Lessons mark it explicitly (:ex[…] for examples, :w[…] for words), so the core checks work for Spanish as well as Chinese (review M2).

What every pack's analysis promises:

  • Readings are citation forms. Stored readings never carry sandhi. Display applies it at render time, keyed by sr: ids.
  • itemKey is many-to-one. One word item bundles every dictionary entry that shares its key.
  • The analyzer never mints an id that isn't a lexicon key. A lemma missing from the lexicon gets no item id.
  • analyze() runs at build time for catalog lines, and their tokens ship in the media files. The app runs it only for mined sentences. That needs a dictionary and the reading data in the bundle, a cost still to be measured.

Compiled lessons

packages/core/content.ts owns the compiled shapes: CompiledLesson, Step, Clip, the curriculum and the manifest. The toolchain writes them and the app reads them, so the app never sees authoring syntax. A lesson file fills the decided arc's slots: :::opener, :::lesson, :::examples and :::practice. Start and Done are generated, and there are no recap or we-do activities. The curriculum, content/zh/curriculum.ts, is plain typed data with no DSL, and a lesson with no file is simply not authored yet.

Events and derive

// packages/core/events.ts: the only write path. One writer, one union.
// TypeScript and the sync wire format are camelCase, and the SQLite columns snake_case; only apps/server maps between them.
interface EventEnvelope<K extends string = string, P = unknown> {
  id: string; kind: K; v: number; lang: Lang | null
  occurredAt: number                // integer ms, clamped at record time: monotonic per device, and a review is never before the card's last known review
  deviceId: string
  deviceSeq: number                 // per-device counter, so a gap is detectable
  build: string; payload: P
  seq?: number                      // server-assigned; absent until pulled
}
type EventDraft =                   // what callers record; the envelope adds the rest
  | { kind: 'review'; v: 1; payload: { cardId: CardId; rating: 1|2|3|4; durationMs: number
      dueAt: number                 // integer ms: the device's load-balanced due date
      prevReviewId: string | null } }   // the review the device treated as this card's previous one
  | { kind: 'trial'; v: 1; payload: { itemId: ItemId; lessonHash: string; widget: `${string}@${number}`; correct: boolean; recycled: boolean } }
  | { kind: 'device'; v: 1; payload: { reason: 'hello' | 'day' } }   // hello: registers the device on first launch. day: proves the device has flushed the previous study day
  | { kind: 'setting'; v: 1; payload: { key: string; value: unknown } }   // synced keys include studyTz (IANA name) and dayStartHour; the latest by (occurredAt, id) wins
  | { kind: 'flag'; v: 1; payload: { note: string; target?: string } }
  | { kind: 'span' | 'exposure' | 'claim' | 'watch' | 'card_added' | 'lesson_cursor'; v: 1; payload: { /* … */ } }
  | { kind: 'void'; v: 1; payload: { target: string; reason: string } }   // target can't be a day_closed
  | { kind: 'day_closed'; v: 1; payload: { date: string; xp: number; credit: 'none'|'floor'|'standard'|'stretch'; rules: Record<string, string>
      minutes: number               // 2 dp
      basis: 'settled' | 'grace' } }

7. Adding curriculum and languages

The toy pack exists from phase 0 and runs the core's test suite, so a Chinese assumption can't creep into the core unnoticed. A lint rule also rejects CJK literals in packages/core.

Add a unit or lesson (content only)

  1. pnpm content:new zh unit telling-time scaffolds the curriculum entry and lesson files.
  2. Claude drafts. content:suggest proposes ingested, lesson-eligible clips for each example.
  3. pnpm content:check must pass.
  4. pnpm deploy (§8). Each device picks up the new build on its next launch.

No code change, no migration. Progress carries over because evidence lives on items. A rewritten lesson gets a new lessonHash, and old trial events keep theirs.

Add a language

  1. languages/ja/{logic,build,views} implementing the three interfaces (analyzer, lexicon, kinds, card templates, sound axes, syllabi, media sources, item views).
  2. Run its importers and the ingester for its media sources.
  3. Write content/ja/ with the same skeleton, templates and core widgets.
  4. Add one line to apps/web/src/languages.ts. A language switcher appears once there are two.

No change to packages/core or other app code, and no migration: events already carry lang. A core change is needed only for a new activity type, such as pitch-accent drills.

8. Runtime flows

A bedtime session (local first)

The session is planned from local state before any network call (review m8), so a slow or missing connection never blocks bedtime. Sync runs in the background while the app is open.

Publishing content (deploying a build)

  1. content:check, then content:build, which writes the compiled content and the media it references, hash-named and listed in one manifest, into the build output, and the web app build, which embeds the build id.
  2. pnpm deploy, one command on the laptop, runs those steps, copies the build to the VPS over SSH on the tailnet, and switches the server to it in one step (§4). CI checks and builds on every push from Phase 6; deploying stays on the laptop.
  3. Each device's service worker sees the new build the next time it's online, and the content loader fetches only the files it doesn't already have. The device keeps running its cached build until the next launch, then switches app and content together, so content can't be out of step with the app that reads it (the old review B1 risk stays closed).
  4. The event log lives in IndexedDB, not in the caches, so it survives an update, and a lesson in progress resumes from its events. If a device loses its storage anyway, a full pull refills everything it had pushed.

10. Cross-cutting concerns

Security and privacy

  • No sign-in: tailnet membership is the only access control. The server binds only to localhost, and tailscale serve (never funnel) is the only way in, over HTTPS.
  • The VPS opens no public port for the app, and SSH is reached over the tailnet.
  • Anything on the tailnet can read and append events, so the tailnet holds only the owner's devices, and a lost device is removed from it (§15).
  • The server treats every pushed event as untrusted input and validates it at the boundary (§5).
  • The ts.net certificate appears in public certificate transparency logs, so the machine and tailnet names are public, though not reachable; neither should say anything private.
  • The backup deploy key lives only on the VPS and can write only the backup repo.
  • Content and media exist only in the private repo, the laptop's media cache, the backup repo, the server and the device caches. Nothing sits on a public URL.

Offline and caching

  • The first load from the ts.net address installs the service worker, which caches the app shell. The content loader then fetches every file in the build's manifest that the device doesn't have, content and media alike, so everything but YouTube works offline after that.
  • Hash-named files never change, so a new build fetches only what changed. The CJK fonts are self-hosted subsets (review n4), cached the same way.
  • The event log and card cache live in IndexedDB in the origin's storage.
  • navigator.storage.persist() is requested once, since a browser may evict an origin's storage otherwise. Evicted events come back with a full pull, and evicted files are fetched again. Phase 5 checks that the installed app keeps its storage on the phone. YouTube lessons need the network.

Backups

  • Every device holds the full event log, so any one of them can refill a fresh server.
  • The server copies its SQLite file off the VPS nightly, to a private GitHub repo (§4).
  • Settings offers a manual export of the log.
  • The media cache isn't in git and costs ElevenLabs characters to regenerate, so it gets the same off-site copy.
  • Phase 6 drills a restore from a device and from a backup file.

Versioning

  • One build id names the app plus content pair, and every event records it. A deploy switches the server to a new pair in one step, so it never serves an app with another build's content.
  • A device runs its cached build until it next launches after an update, so two devices may run different builds for a while. An event whose kind or v a build doesn't know is kept and synced, and derive skips it until that device updates.
  • Trials and spans also record lessonHash and widget@version.
  • Event payloads carry a v per kind. Derive rules are versioned, and FSRS is pinned.
  • Nothing frozen or compared across devices may depend on an unrounded float, since V8 and JavaScriptCore can differ in the last digit.

Licensing

  • A license record on every dataset and clip; the build fails without one.
  • A credits page is generated from those records.
  • Share-alike data (CC-CEDICT) stays in a separate overlay.

Testing

  • Golden fixtures for derive and for SRS replay, including two-device interleavings.
  • A failing fixture for each check rule.
  • Core tests run against the toy pack.
  • Server tests against a real SQLite file: idempotent push, serialized concurrent pushes, per-event rejections, pull paging.
  • A phone-sized end-to-end smoke test of one lesson.

Performance budget

  • App code under 200 KB gzip, for start-up time, with zod stripped from runtime and Cytoscape lazy-loaded (review n3).
  • A lesson is playable within 1.5 s once the app is warm.
  • Build size (content and media) is measured on every build, since every device caches all of it (§15).
  • A full derive over a year of events is measured on the real phone, since the §5 figure is an estimate.

11. Localization (support language)

Two language settings are independent:

  • The target language is what's being learned. It comes from a language pack (zh), and its text (examples, transcripts, items) is never translated.
  • The support language is what the app and the lessons are explained in: English now, Chinese once the owner wants full immersion.
Switching the support language is a setting, recorded as an event. Adding one is writing a new column.

Catalogs are tables, one column per locale

  • apps/web/src/i18n/ui.tsv: app chrome (buttons, labels, feedback lines).
  • content/<lang>/l10n/lessons.tsv: support text from lessons (titles, idea lines, explanations, prompts, option labels). content:build adds a row for every new English string and leaves the other cells empty.
  • content/shared/l10n/terms.tsv: fixed translations for recurring terms (tone → 声调).

How a string resolves

  • The key is the English text itself, plus an optional context column when the same English needs two translations. Authors keep writing plain English in lesson files, with no key naming.
  • Lookup goes through the chosen locale's column, then falls back to English. A half-filled column is usable.
  • Strings use named placeholders ({n}) and separate rows for singular and plural (writing style rules 17–18).

Check rules

  • Coverage per locale (a warning, not an error).
  • Stale rows whose English no longer appears anywhere.
  • Placeholder mismatch between columns (an error).
  • Terms-table consistency.
  • Word budgets, applied to the English column.

What is not a column

  • Target text, never.
  • Bridge glosses (dictionary meanings, sentence translations) are English data from CC-CEDICT or authored. In Chinese mode they stay available behind the Meaning and tap reveals.
  • Chinese-to-Chinese definitions would need a separate, openly licensed monolingual source. That's a dataset decision for later, not a column.

Bundle format: each locale compiles to its own hash-named strings.<locale>.json. Lesson files reference strings by hash(en, context), so switching locale loads one small cached file, and adding a locale changes no lesson file. The activity pilot (sandbox/spikes/activity-pilot) runs this end to end with an English/中文 toggle.

15. Risks and open questions

RiskMitigation
Too few lesson-eligible clipsAISHELL-3 and AISHELL-1 supply native sentences, and ElevenLabs v4 covers the gaps and generated sentences (README Native audio and TTS row)
The VPS is a single point for sync and first loadsEvery device keeps working offline from its cached build and its full local log, and the outbox waits. A lost VPS is replaced by renting a new one, deploying, and refilling the SQLite file from the nightly backup or from any device (Phase 6 drills both)
Tailscale has an outage, or the account has a problemThe same as above: devices keep working offline, and only sync and first loads wait. SSH to the VPS goes over the tailnet, so recovery without it goes through the provider's console
The SQLite file is corruptedWAL mode with one writer process. The nightly copy is taken with SQLite's online backup and checked with PRAGMA integrity_check before it's pushed, so a bad file isn't backed up silently. Restore the last good backup and let each device push what it holds; pushes are idempotent, so nothing doubles
Build size grows with the media, since every device downloads and caches all of itOpus for speech and WebP for images, and hash-named files, so a new build downloads only what changed. Size is unmeasured; measure it per build, and at the scale check, against first-load time and the phone's storage. If it gets too big, that reopens how media is cached
The backup repo outgrows GitHubGitHub refuses files over 100 MB, and the SQLite copy grows with the log. Compress the copy and measure it with the media cache at the scale check; if either nears GitHub's limits, split the file or move the copy
